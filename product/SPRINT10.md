## 1. One customer outcome and a bounded first slice

A new shop owner proves control of their mailbox, creates or resumes exactly one tenant, saves their answers, receives a useful draft immediately, and reaches an authenticated phone-usable workspace. The owner can review the actual rules, run an isolated customer test, inspect the result and understand the exact next activation step without Steve creating a record, sending a private portal link or reviewing routine setup manually.

The first draft is deterministic from saved owner answers: `build.status=built`, `source=owner_answers`. Optional website input is retained as an input but is **not crawled or represented as imported**. New tenants use `onboarding.version=1`; their legacy background build and paid provisioning paths remain disabled. No asynchronous queue is required to make this already deterministic draft appear. Unknown business facts remain unknown and block only capabilities that need them.

The first slice can prepare and activate **website chat only when its own current requirements are satisfied**. Phone/SMS are explicitly inactive; Calendar is not implied. Fake/no-model mode may demonstrate saving, review and isolated testing but must leave the model-readiness blocker visible. Customer OAuth, legal declarations, costs and forwarding remain deliberate customer actions in later slices. Billing and recharge stay off. This sprint authorizes no model/provider request, message delivery, purchase or deployment.

## 3. Executable ticket acceptance

### S10-01 — Verify the mailbox and recover without founder help

Trace: SELF-SERVICE A0-01/02/05/08; QA ACCESS-01/03/04/08/09/11/12.

- `POST /api/access` link requests have the same generic public result for new/existing mailboxes. No slug, owner credential, private configuration or verification token is returned. A request alone changes no tenant.
- Links have a trusted fixed application destination; no caller-supplied redirect. Challenge hashes expire after **20 minutes**, exchange is single-use under a race, and successful proof issues a separate **24-hour**, scoped, hashed session. Browser history removes the verification fragment. Replayed, altered, expired and delivery-failed tokens do not admit an owner.
- Disallowed origin, malformed/oversized input, unsupported method, recipient/IP throttling and strict storage failure produce bounded errors without a tenant write or unplanned send. Emails/tokens/session values do not enter general logs.
- Sending disabled/rejected is a useful retryable error, not “email sent.” The local test outbox is a private injected fixture, never a production bypass or public token endpoint. Real inbox delivery is a separate future controlled gate.
- Expired/reused links and failed exchange offer another link. For new `onboarding.version=1` tenants, the current 24-hour bearer authorizes onboarding, owner reads/writes, exports and private tests; sign out revokes its server record and clears browser authority/private UI. The workspace URL contains no permanent `k`, and a permanent key alone cannot authorize these tenants. Explicit expired/revoked authority fails rather than falling through to public data. Legacy unmarked shops retain their prior key path; this is not a global legacy migration or an HttpOnly-cookie implementation. Already-authorized server invocations may finish after revocation.

### S10-02 — Create once and resume the right tenant

Trace: A0-03/08; ACCESS-02/04/05/06/07/12.

- `/api/onboard` requires verified session authority. Body email cannot substitute for it or select another account; missing/foreign/expired/revoked authority is rejected **before** client/index/event/build/provision changes or disclosure. Retest the exact baseline takeover input, not only the new entry API.
- The strict CAS account registry reserves one stable tenant identity and canonical initial submission. Two sessions/double submit/retry after response loss create one tenant, preserve the same owner identity and resume a partially completed projection. Conflict/lost-response injection covers each authoritative write; storage failure is not “account absent.” No side effect runs inside a replayable CAS callback.
- Recovering an existing verified owner returns the existing workspace without resetting live/paused/cancelled status, rules, contact data, number, Calendar state or provider receipts. Changed questionnaire values during pending creation conflict or require review; they cannot silently replace the reserved submission.
- A/B accounts cannot read or mutate one another, including progress/exports. Explicit invalid owner credentials fail as owner access and give a clean UI recovery state; they must not fall through to a public widget response that crashes the portal.

### S10-03 — Resume saved answers and get a truthful draft immediately

Trace: A0-04/05/08; ACCESS-10/12; OM first-slice owner-answer decision.

- After verification, the phone form saves bounded owner fields and current step with a revision. Reload, Back, leaving/returning and a lost final response restore the same saved state. Two-tab stale saves cannot overwrite newer answers. Failed save stays visibly unsaved, preserves the current draft and offers retry; do not navigate as though it succeeded.
- Website is optional. No website, unreadable/private/internal/hostile URL and untrusted text cause **no crawl or model request in this slice**. The portal says the draft is built from owner answers, not from a website it did not read.
- Successful create returns the stable owner-fact draft without founder action, paid model work, background trigger or provisioning. Missing fees, hours, service area and booking policy are not invented or represented as reviewed. Required facts produce actionable readiness blockers.
- Both ordinary and failure/retry paths preserve owner facts. A failed/partial write does not become a successful build; repeated create cannot rebuild over later owner edits. Legal/tax details are optional until a selected channel needs them, and no card/payment is taken.

### S10-04 — Try a real tenant's rules without touching real customer work

Unknown data remains unknown; no test result claims a real appointment, delivered alert or dispatch.
- A successful completed test stamps the exact configuration revision. Failed, interrupted or stale-rule tests cannot certify a changed revision; material rule changes invalidate prior test/review. Separate sandbox history cannot leak between tenants or into public conversations.

### S10-05 — Activate only eligible website service

Trace: A0-05/06; QA LIVE-01 and central bypass cases.

- One server readiness function returns current revision, per-channel readiness/activity, blockers and useful in-portal next actions. The portal displays it; `go_live` and `resume` recheck it atomically rather than trusting tutorial state, posted `ready` or stale UI.
- Website activation needs complete current owner facts, safe handoff destination, current saved review, successful isolated test and available model capability. Missing/fake model is an explicit blocker; a local fake test never proves production service. A helper fixture may model an available dependency without making a paid call, but that proof must be labeled.
- Failure preserves prior state and names missing requirements. A material edit makes old review/test insufficient and cannot leave customer service running under an unreviewed revision. Pause/cancel disable new web use; cancelled state and stale workers cannot reactivate it. UI distinguishes configured/ready/active/installed.
- For new self-service tenants, phone/SMS remain unready/inactive across API, UI, welcome messages and public routes. New-marker direct worker invocation, provision action, inbound SMS/voice/Vapi and public pre-live chat cannot bypass the disabled channel. No automatic number buy, carrier filing, assistant creation, phone routing, send or Calendar action.
- Existing accepted manual-availability/capacity, emergency order and legacy tenant behavior get targeted regression; do not silently broaden this first-slice migration into a claim that all old channel paths were reverified.
- Every accepted new-tenant AI reply turn, including a failed or ambiguous model attempt, reserves a strict shared CAS allowance before model or conversation/test writes: private 20 per tenant/day, public web 50 per tenant/day and global 50 across all such tenants and both modes, resetting at Houston midnight. Internal bounded SDK/tool retries do not create extra logical turns or refunds. Remaining allowance is constrained by the shared ceiling; private-only exhaustion need not disable eligible web service. Exhaustion returns 429; unreadable/inconsistent state or invalid configuration fails closed503. Zero global allowance is the operator kill switch. Owner-only detail, honest disabled widget and no active badge after shared exhaustion are required UI outcomes.

### S10-06 — A useful guide tied to real saved actions

Review completion follows saved current rules; test completion follows the current successful sandbox result; activation follows authoritative readiness. Clicking Next cannot manufacture any of them.
- At 390px and by keyboard, required controls, validation, save state, owner result and next action are reachable and readable without overlap or focus traps. Invalid/private/expired access, offline/save/read/test failure, stale revision and cancelled state all yield useful recovery without uncaught errors or endless loading.
- Returning owners resume meaningful work/setup, not a destructive repeat signup. No routine admin edit, manually sent portal link, Steve review or “we will call you” dependency appears. The customer still performs their own deliberate mailbox/provider actions.

## 5. Requirements decisions and work deliberately left open

1. **Immediate deterministic draft versus queued import.** The owner-fact fast path is required now; do not force it through a new async queue. 2. **Identity migration.** New-marker owner authority now uses the same current, revocable 24-hour server session across onboarding, workspace, CSV and private tests; new portal links contain no permanent key. Sign out revokes future reads/writes and clears private UI, while already-authorized server work may finish. Legacy unmarked shops retain prior key authority. SessionStorage remains the browser transport; HttpOnly-cookie adoption, team roles, legacy migration and single-use OAuth state are later security work. New-marker OAuth/billing calls are disabled before provider actions.
3. **Eligible web service versus installation/delivery.** A ready/active website channel is distinct from an observed exchange on the customer's installed widget. Fake local readiness is neither actual inference nor customer delivery. Real email/model/live-store proof requires its own authorization and receipts.
4. **Activation versus full autonomous operations.** Paid provisioning stays off until durable intent/receipts, current consent/cost controls, ambiguous-result reconciliation and controlled delivery/cleanup acceptance exist. Durable reminder/outbox execution, Calendar repair, cancellation cleanup and honest completed-contact metrics remain separate ranked work. No checkbox closes them.
5. **Commercial and human language gates.** Billing is parked; setup takes no payment and may not claim card capture or automatic billing. Named-shop Spanish safety review and first-customer case19/real-provider/first-week gates remain open. A homepage demo's accepted Spanish or audio exchange is not that proof.
