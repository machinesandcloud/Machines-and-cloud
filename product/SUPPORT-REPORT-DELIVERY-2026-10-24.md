# Owner report to operator review and owner feedback

This slice repairs the existing Inbox report workflow. An authenticated owner reports one saved conversation, returns to see its progress, and receives an operator's customer-visible resolution in that same context. It uses the existing owner/operator APIs, client record, Issues view, audit and ordinary scheduler. It creates no new helpdesk, message channel or independently mutable issue queue.

## Retained source and access

`client.management.supportReports` is the conditional source for both owner progress and operator Issues. Saving a report atomically saves its operator attention authority; it does not depend on an initial email, task or index write. `reported`, `acknowledged` and `resolved` are distinct. A saved case means it is available in operator Issues, not that a person received an email or repaired the front desk. Acknowledgement records review starting; resolution requires a separate public explanation after acknowledgement.

Each case binds the current workspace incarnation, conversation, immutable owner operation and a snapshot of the latest six messages, each at most1,000characters. The operator sees that bounded context and the ordinary existing customer conversation/rules/recovery tools. The owner sees the note, reference, status/times and public resolution. Operator action reasons, actor mailbox and internal notes stay private. Report fields cannot be used to change service status or activate a provider.

Owner creation accepts only `report_conversation`, channel/contact, a useful3–1,000character note, one32hex operation and null/current resolved-report revision. No browser-supplied case ID is trusted. The handler validates the actual owned saved conversation and rechecks the verified session within the client CAS before committing. Existing active reports cannot be duplicated. A new problem after resolution requires an explicit new operation and the current resolved revision; it does not reopen the old case.

Operator `acknowledge_report` and `resolve_report` use the existing customer management revision plus the case revision and operation ID. Resolution has a separate10–2,000character public explanation; a private reason remains required for audit. Current operator session, allowlist and tenant are rechecked at the mutation. A stale decision cannot replace newer work. Paused/cancelled service accounts can still report and receive support; support does not resume service.

Both owner and operator replay the exact same operation and normalized body, including semantically reordered JSON properties. A different payload using the same ID conflicts. Replay runs before capacity/latest-revision checks and returns current case state, even if an operator has since resolved it. The immutable `reportOperationId` and bounded `operationIds` let returning browsers reconcile a lost response without inventing a new case or repeating a completed decision. Retention is bounded to100cases; that blocks only another new case, never replay, acknowledgement or resolution of retained work.

## Ordinary recovery

New cases need no attention projection or physical conversation-flag rewrite: owner report association and operator Issues derive from the same client CAS. Consequently an old open task cannot resurrect a resolved case, and an old resolve cannot clear a later case. Conversation messages remain independently retained and are never replaced by report maintenance.

Earlier supported-tenant owner flags are adopted into this source by the existing scheduler's `supportReportRecovery` block. Adoption requires the exact current tenant namespace, a real saved conversation, an owner flag and a useful note/time. Unbound/foreign flags are not attributed to a recreated workspace. Empty flags left by the old Cancel bug do not become invented reports. A stable operation derived from the retained flag prevents duplicate adoption; an existing canonical case takes precedence over an older flag, including after resolution.

Recovery examines at most four client candidates and eight conversation keys per client and checks a four-second deadline before further candidates/conversations. It reuses the existing bounded metadata enumeration (at most two page requests per scan), limits that metadata view to2,000keys and records incomplete/error health rather than claiming a complete scan beyond it. Retained client/conversation cursors advance fairly; before a local cursor write, recovery checks that its observed cursor still matches current storage. Empty/no-change scans do not mutate customer records. A failed read/write remains retryable through the ordinary next invocation, without a manual dispatcher or founder database edit. This is local retained-record recovery, not an external notification send.

## Experience and acceptance boundary

The existing Inbox entry becomes **Report a problem**. An accessible form asks **What went wrong?** and requires explicit **Send report**. Cancel/Escape/backdrop saves nothing and returns focus; multiline Enter is not submission. Saved progress uses **Reported**, **Under review** or **Resolved**, one reference and the public explanation. The operator finds the same report in existing Issues/customer details and uses report-specific review/resolution controls. Lost results retain the original operation/draft for status checking and safe same-body replay; sign-out clears private recovery state.

Engineering/independent QA exercise actual handlers, conditional storage and returning/error/recovery paths. UI engineering and independent QA observe actual desktop/mobile assets. Passing this local job is narrower than actual named operator/backup mailbox receipt, continuous staffing, funded hosting continuity, provider-failure escalation or a controlled operational incident. Those G8 production/operations requirements remain open. No new email/SMS/provider authority or delivery claim is introduced by this slice.
