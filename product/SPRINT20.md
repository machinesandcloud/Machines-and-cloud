## Calendar policy and live acceptance preparation

Private Functions variables are `CALENDAR_EXECUTION_POLICY_JSON` and `CALENDAR_EXECUTION_APPROVED_VERSION`. The strict policy supplies version/expiry, `clean_initial` or `reviewed_retained` census mode, exact tenant identity, Google-client hash, target-calendar hash, authoritative census digest, one to ten visit IDs and explicit action/total request limits. Both `CALENDAR_CONNECTION_ENABLED` and `CALENDAR_DELIVERY_ENABLED` remain required for delivery. Absent/malformed/expired configuration makes execution unavailable; no customer-facing provider IDs or private policy details are exposed.

A concrete live packet must identify a fresh controlled owner/workspace, retained-resource census, planned normal owner visit ID, owned calendar and exact effect/request limits before activation. The desired result is normal signup/return → owner Google consent → Add visit → observed matching event → move → observed update → cancel → observed deletion, retaining the local cancelled record and delivery receipts. No attendees/invitations or customer SMS consent may be inferred. Owner password/MFA/OAuth decisions remain with the owner. A consumed/failed sign-in link is a failed signup step, not permission to change authentication or reset a closed email allowance.

Netlify uses function environment values from the deployment. Policy/gate changes therefore need a build/deploy; compile the exact policy before proposing one approved build. See [Netlify documentation](https://docs.netlify.com/build/functions/environment-variables/). An environment-only update must not be presented as live activation. If the tenant/visit cannot be known before the release, separate the phases and obtain the actual additional build scope rather than silently consuming it.

The [release preflight](../scratchpad/core-delivery-release-preflight.json) records the14-file application manifest and accepted checks; the [independent disposition](../scratchpad/core-delivery-independent-disposition.json) confirms exact source and excludes eight older main runtime files. The [controlled live proposal](../scratchpad/core-calendar-live-proof-proposal.json) describes one build, up to3 sign-in emails, one internal workspace and one synthetic event lifecycle, with durable request limits and explicit cleanup. The fresh scratchpad request controller passes15 offline checks and has independent architecture review. It reserves requests/effects durably, rejects reused ledgers and unapproved targets/actions, and still requires caller-supplied browser/mailbox/publication adapters. It is not a completed live journey. The packet remains a proposal. No live packet is approved in this sprint yet. Keep all real execution gates unchanged. The repo's one-build-per-day rule still applies; publication and actual service tests require concrete bounded approval after local review. Do not push main wholesale.
