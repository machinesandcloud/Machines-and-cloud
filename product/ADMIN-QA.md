## Selected first slice and acceptance contract

Root selected `/api/manage` with a separate `operator` challenge/session scope, fixed admin return, eight-hour sessions and `ADMIN_EMAILS` authorization checked on every request. Owner access remains the separate onboarding scope and 24-hour lifetime. A missing operator allowlist fails closed. The new portal must not reuse an ordinary customer bearer, put a shared bootstrap key in storage, or emit a permanent owner credential.

The selected management actions are new-self-service pause/resume, website service cancellation, bounded business-rule correction, operator note, workspace rebuild and safe operation retry. Each mutation needs an identified actor, a reason, expected revision, conditional state write and an audit record that must succeed before the state change. Cancellation retains provider identities and customer records; it does not release a number or cancel a provider subscription. Closed accounts permit internal support notes while service changes remain blocked. Legacy tenants are read-only in the new portal. The old CLI-compatible admin API needs explicit new-tenant safeguards and redacted read responses; compatibility does not authorize normal-browser exposure of its credentials.

The first real background kind is deterministic `workspace_rebuild`. Initial account creation keeps its existing inline deterministic build. A rebuild operation is durable before execution, stable for tenant/kind/input revision, conditionally claimed, bounded to three safe local attempts and recoverable through its completion receipt. The scheduler scans at most 50 candidates and runs at most 10 jobs per invocation using a durable fair cursor. No crawl, AI call, customer contact, purchase, carrier filing or activation belongs to this kind.

Unknown or future onboarding versions must not become legacy implicitly. Enabling a connection by deleting the marker, changing its version or writing a status flag is not an accepted migration.

## Independent execution and returns

The first actual-handler run passed36/36 in `scratchpad/operator-management-qa-first.json`. It exercised both in-memory storage and the installed Netlify Blobs SDK against an intercepted conditional-write fixture. Three forced CAS conflicts were observed. All unexpected server destinations were denied; intercepted sign-in payloads in the SDK fixture were not delivered.

The expanded run in `scratchpad/operator-management-qa-expanded-first.json` passed42/43 and exposed a real worker race. Generation1 checked its separate operation lease, then its client result write was held. Generation2 reclaimed the operation after expiry and failed its result write. Releasing generation1 allowed its old result and receipt to commit. The first failure remains preserved. Architect replaced this cross-document check with an authoritative conditional fence inside the same client document as the result and receipt. The final independent fixture holds generation1's result write, advances only the clock, commits generation2's client fence, fails generation2's result and releases generation1. The stale result is rejected; a later generation3 completes safely. Six conditional conflicts were observed in the final API run. Lease expiry permits a takeover; a newer committed client fence rejects an already dispatched old write by ETag.

Two later queue/exception returns are also retained. `operator-management-qa-queue-race-first.json`53/54 shows an old completed queue removal deleting a newer accepted same-revision repair after412/retry; queue tokens now fence that removal. Architect subsequently added monotonic exception resolutions so a delayed older failure could not reopen a newer success. Independent `operator-management-qa-watermark-first.json`55/56 then exposed the reverse race: observing a running final attempt incorrectly advanced that resolution and suppressed its later genuine failure. The final implementation advances resolutions only for known terminal resolution or a durably accepted explicit retry. Both orderings pass independently: old failure after newer success keeps openFailures0, and final-attempt failure after a concurrent running observation keeps openFailures1.

Additional passing actual-handler cases cover known committed support changes whose optional detail projection fails, persistent failure visibility after exhausted work leaves the queue, explicit retry audit and cumulative attempts, owner exclusion of staff notes, owner/operator and cross-owner isolation, legacy full-read redaction and blocked legacy mutations on both current and future onboarding markers. No receipt is treated as evidence of phone activation, customer contact or a provider delivery.
