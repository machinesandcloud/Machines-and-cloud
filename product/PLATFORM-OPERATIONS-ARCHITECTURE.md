# Customer operations architecture

October 22, 2026. This extends the verified customer workspace and acquisition flow. The target is routine customer setup and recovery without founder involvement. It does not authorize deployment, provider calls, AI requests, email delivery, purchases or billing changes.

## Identity and management

The customer remains identified by the existing verified, expiring, revocable access session. A separate operator capability is granted only when that session's normalized mailbox appears in an explicit server-side administrator allowlist. An ordinary customer cannot request this capability. Missing allowlist configuration fails closed. An operator sign-in proves mailbox control; it does not replace OAuth authorization for a customer's Google account, carrier declarations or explicit cost acceptance.

The current shared `ADMIN_KEY` API is a compatibility surface, not the target customer-management login. A new managed customer view must omit owner keys, OAuth tokens, provider credentials, raw EIN and hidden lead-source secrets. Customer navigation does not impersonate a mailbox by appending an owner key. Support work needs an identified operator and bounded, audited actions rather than editing the entire client object.

## Durable work and the first executable job

Keep initial owner-fact draft generation inline inside the existing stable account reservation. That deterministic fast path already completes without a background dispatch; adding a queue there would create a failure dependency.

The first durable job is an explicitly requested workspace rebuild or repair from the owner's saved facts. It does not crawl a website, call a model, contact a customer, buy a number, create an assistant, submit a carrier registration or enable a channel. The job's stable identity includes tenant, job kind and configuration revision. Repeated requests at the same revision return the same work and completion receipt.

Persist the operation before executing it. Each record retains its tenant, kind, input revision, state, creation/update times, attempt count, due time, claim token/generation and sanitized result or failure code. The worker reads the latest client, verifies current ownership/state/revision, and obtains a conditional claim before work. It commits a narrow revision-checked patch, preserving business facts, provider IDs, calendar credentials, customer records and unrelated owner changes. A completion receipt in the same client write lets a later attempt repair the operation record after a lost response without repeating accepted work.

Only this deterministic local job may recover an expired worker claim through a bounded retry. An uncertain external purchase or send cannot reuse that rule. There is no production provider adapter in the first operation kind.

## Recovery and observability

The regular scheduler includes a bounded setup recovery block on every invocation, independent of the legacy half-hour channel scans. A durable fair cursor considers at most 50 due candidates and executes at most 10 jobs per run. Conditional claims prevent overlapping scans or workers from completing the same revision twice. Three accepted attempts per operation bound recovery. A stale input revision is superseded; paused or cancelled clients cannot be rebuilt or activated by an old claim.

Owner progress exposes operation ID, label, state, last update, next safe action and a bounded reason. Operators additionally see attempts, next retry and a correlation ID. Storage/read/list failures remain visible failures; no missing read becomes an empty queue or success. Completion means only the job's recorded outcome. A rebuilt workspace is not activated website chat or working phone, text or Calendar delivery.

## Connections and later adapters

All requested connections stay inside the same customer journey. Saving connection preferences records desired service only. Phone/SMS work must separately record the customer's versioned authority and actual cost acceptance, and a product-wide execution gate remains off until accepted. Calendar requires customer-owned OAuth with one-use server state and token recovery. These are deliberate customer actions; routine execution after them is platform work.

Future irreversible adapters require a durable request intent before dispatch, supported provider correlation/idempotency, persisted remote receipts and explicit reconciliation after uncertain responses. A timeout or lease expiry never authorizes a repeat purchase. Cancellation retains remote resource IDs until cleanup is confirmed. Signed provider callbacks update only their matching operation and cannot activate stale or cancelled work. Billing remains parked.

## Required local acceptance

Use memory and the installed Blobs SDK protocol double with every outbound destination blocked. Verify duplicate requests, concurrent workers/scans, lost dispatch, stale claim fencing, known local failure and bounded retry, completion-receipt repair, owner edits during work, pause/cancel, unauthorized/foreign mailbox access, private sanitized DTOs and fair progress beyond 50 queued candidates. Run existing account, scheduler, owner-test, delivery and AI limits regressions. QA must independently exercise the customer and admin UI against the real local handlers. Local fixtures do not establish hosted storage concurrency or provider delivery.

## Implemented helper contract and engineering receipt

`netlify/functions/lib/platform-operations.mjs` implements `queueWorkspaceRebuild`, `listWorkspaceOperations`, `retryWorkspaceOperation`, `recoverWorkspaceOperations` and the sanitized `workspaceOperationView`. Queue/retry callers supply the current configuration revision and an identified actor `{role: "owner" | "operator", email}` with a reason. HTTP entry points remain responsible for proving the operator role; the helper independently checks owner mailbox, supported self-service version, current tenant identity and revision. Unknown onboarding versions cannot run this job.

The canonical active intent is committed before the operation projection. Its fair lexicographic cursor survives completed entries being removed, and recovery reconstructs missing projections. The active index accepts at most 1,000 entries and rejects additional requests before claiming they were saved. Each scan considers at most 50 candidates and executes at most 10 jobs. Counts in the returned receipt are explicitly scoped to those candidates; they are not a census of historical customer health.

Every new queue intent or accepted explicit retry carries an opaque queue token. Completion removes only the exact token selected by that worker. An older completion cannot erase a newer same-ID repair or retry while its conditional cleanup write is delayed. The phone queue applies the same rule to preserve a newly accepted cancellation against an older acquisition completion.

A worker claim lasts 60 seconds and carries a random token plus increasing generation. Its authoritative fence is `workspaceOperationClaims` in the same conditional client document as the result patch. That fence commits before the secondary operation claim is recorded. A newer committed fence changes the client's ETag, so an old delayed result cannot commit even when the newer result fails. Lease expiry permits a fenced takeover; it does not retroactively revoke an already in-flight HTTP write by itself. The earlier cross-document claim check failed independent QA's delayed-write case; the failed receipt remains retained rather than being presented as acceptance.

Three automatic attempts are allowed. An explicit authorized retry of an exhausted local refresh grants three further attempts, retaining cumulative attempts and a bounded audit of the latest 20 retry requests. The client patch and a revision-keyed receipt commit together; the most recent 20 client receipts are retained. Recovery checks that receipt before another attempt or an exhausted-claim decision, so a lost completion response can be repaired without rewriting the draft. Operation records retain the longer per-revision history; owner lists return the most recent 20 records.

An owner or operator can explicitly repair a paused workspace while it stays paused. The request captures lifecycle state and its monotonically updated operation epoch. Old work queued before pause/resume/cancellation cannot revive after a complete state cycle. A cancelled workspace cannot be refreshed. A newly authorized repair of the same configuration can reuse the stable operation ID with an audited request generation and another bounded attempt budget. Older completion receipts do not certify that new cycle. A completed older fence can be replaced immediately by the new request's conditional fence; a customer need not wait for its old 60-second lease merely to repair a failed build. No repair turns on a channel.

The optional `/api/operations/recover` background worker accepts only a dedicated `WORKSPACE_WORKER_KEY` header and bounded JSON options. With no key configured it is unavailable. The scheduler calls the recovery helper directly, so regular recovery does not depend on that optional dispatch or key. The worker cannot accept a tenant, model, provider operation or arbitrary function name.

An internal failure index retains exhausted operation IDs, tenant, code and time after active work is removed. Recovery commits that projection before deleting the repair intent; a failed projection leaves the intent available for repair and cannot produce a healthy result. The public scheduler receipt exposes only a global `openFailures` count and bounded error codes. Its `ok` remains false while any recorded exception remains, even when the current scan has no candidates. A durably accepted retry or resolution clears the matching exception. A monotonic generation/attempt watermark is written even when the old failure is not yet projected, so its delayed write cannot reopen an already resolved exception. Index errors never silently dismiss it.

Engineering's [first 26-check receipt](../scratchpad/platform-operations-engineering-first.json) and [27-check exception receipt](../scratchpad/platform-operations-engineering-exceptions.json) remain preserved. The [current 35-check receipt](../scratchpad/platform-operations-engineering-resolution-final.json) covers client-document fencing, immediate same-ID paused repair, old receipt rejection, bounded retries, exception persistence and failed projections, ambiguous committed writes, 65-customer fairness, selected-intent cleanup and both delayed-failure resolution orderings in memory and the installed SDK protocol fixture, with zero external requests. Only accepted explicit retries and actual terminal resolutions advance the exception watermark; observing running work cannot suppress its later failure. [Independent management QA](../scratchpad/operator-management-qa-resolution-final.json) passes56/56 on the same runtime. Admin/customer browser outcomes remain separately recorded; none is hosted or provider acceptance.

## First real connection adapter: number acquisition only

`phone-activation.mjs` implements one first-number acquisition intent per verified customer identity. Browser submission keys do not create independent purchases. The stored intent binds the current rules revision, exact versioned offer digest, quoted cost caps, authority text, owner mailbox and separate explicit authority/cost acceptance. Its durable active intent precedes the operation projection. A conditional claim and acquisition-start marker precede the only purchase dispatch. A lost or expired request becomes `uncertain`; it never becomes permission to purchase another number.

`phone-twilio.mjs` is a real Twilio adapter used by the same engine as local fixtures. It reads account-specific US local-number pricing and eligible inventory, submits one IncomingPhoneNumber request with an opaque correlation label, records the SID/number/request receipt, and reconciles through reads. It does not create voice assistants, attach customer routing, submit texting registration, send messages, or set a service live. `number_acquired` means a reserved number, with `active: false` throughout this slice.

The [Twilio IncomingPhoneNumber reference](https://www.twilio.com/docs/phone-numbers/api/incomingphonenumber-resource) documents create, SID read, FriendlyName filtering and SID deletion. FriendlyName is only a correlation aid; it does not provide a documented uniqueness or purchase-idempotency guarantee. The adapter accepts one exact account/label match, treats multiple matches or pagination as unresolved, and never treats an empty correlation search as proof that a timed-out create did not happen. A known SID returning 404 can confirm that specific resource's absence during cleanup. Deletion is followed by a read before release is presented as confirmed.

The [account-specific Phone Numbers Pricing API](https://www.twilio.com/docs/phone-numbers/pricing) supplies the current monthly price by country and number type. [Twilio's billing explanation](https://help.twilio.com/articles/223182908) says provisioning incurs the full monthly charge up front and recurring charges continue until release. The adapter checks its pricing read against the accepted server offer before purchase. The create response does not contain a charged-amount receipt or a conditional maximum-price parameter. Stored pricing evidence is a quote or remains unconfirmed after reconciliation; it is never called an invoice or a hard provider-enforced dollar ceiling. Price changes between read and create remain a production acceptance issue.

Production execution defaults off. It requires `PHONE_ACQUISITION_ENABLED=true`, a valid unexpired `PHONE_ACTIVATION_OFFER_JSON`, matching `PHONE_ACTIVATION_APPROVED_VERSION`, and provider credentials. The server offer specifies `scope: number_acquisition_only`, US area code, USD one-time/monthly/cap amounts, expiration and the exact authority text. A caller cannot supply an adapter, execution gate, arbitrary price or test mode. The fixture injection factory is separately restricted to test mode and a loopback site. No environment gate or provider account was changed during implementation.

The reachable owner API exposes sanitized `phoneActivation` status and an offer only when the full policy is available. Its explicit `request_phone_activation` action accepts only the current configuration revision, opaque submission key, offer version/digest and separate true authority/cost choices; the verified actor is taken from the session. Only `testing` and `live` supported workspaces can authorize or dispatch a new acquisition; paused, cancelled, archived and unknown states cannot. The worker rechecks the latest customer and intent after its claim, and the real adapter checks again immediately before the purchase POST after its pricing/inventory reads. These are bounded authority checks, not a transaction with the remote provider.

`cancel_phone_activation` records customer cancellation using the stored intent and current owner authority even when the current offer is expired, removed or unavailable. Operators see progress and unresolved setup issues but cannot accept costs or authority on a customer's behalf. A dedicated `phone-activation-scheduler.mjs` runs every ten minutes, at most one phone job per invocation. All provider requests share a 15-second aggregate deadline for that invocation and each HTTP call is limited to at most five seconds of its remaining budget. The main legacy scheduler reads only its durable health receipt and pending-work counters; it does not dispatch provider work. The browser can close safely.

Cancellation retains resource receipts while release is pending or uncertain. A lost release response is reconciled by the original SID. A confirmed still-existing SID can be retried for cleanup; a missing acquisition result cannot be retried for purchase. A cancellation racing a purchase preserves the eventual receipt and directs it into cleanup. The original SID is retained as history even after confirmed release.

Completed lookups clear only their own claim token. A completed acquisition lookup cannot delay an immediate subsequent cancellation/release reconciliation, and an older lookup cannot clear a newer reader's token. With execution disabled, local projection/cancellation repair remains safe, pending or uncertain work remains visible, and no provider request is made. `needs_review` remains a durable nonexecuting queue exception. A fresh failed phone-worker receipt keeps health unhealthy even if the current queue is empty. Counts inspect at most 50 entries; a larger pending queue returns `phone_scope_partial` and cannot be advertised as globally healthy.

The [initial 22-check phone receipt](../scratchpad/phone-activation-engineering-first.json) remains preserved. The [current 30-check engineering receipt](../scratchpad/phone-activation-engineering-lookup-release-final.json) exercises memory and the installed SDK fixture, plus the actual production Twilio adapter through intercepted pricing, inventory, create, correlation, delete and confirmation reads, including the combined lost-create → lookup → immediate cancellation → lost-release recovery. All network destinations are intercepted; no real provider request or environment activation occurred. The [independent 42-check phone receipt](../scratchpad/phone-activation-qa-lookup-final.json) accepts the current production exports, owner HTTP authority, paid-state guards, quote removal/expiry, uncertain writes, deadline, health visibility, delayed queue cleanup and immediate combined reconciliation. The [35-check browser journey](../scratchpad/phone-onboarding-ui-accepted.json) separately verifies customer choices and operator visibility. These are local functional proofs, not provider delivery acceptance.

Still required before paid activation: approved customer cost and authority wording; account-specific spend policy; controlled provider acceptance; resource/routing/fallback reconciliation; a tested customer-forwarded call; texting sender registration and delivery/opt-out proof; safe customer Calendar OAuth and event reconciliation; and a reviewed renewal/replacement intent after this first-number lifecycle. An operator can inspect uncertainty here, but a manual supported match/attachment and reconciliation action is not implemented; editing raw JSON or using the old shared key is not accepted completion. The production gates stay off. This slice does not establish fully automated phone, SMS or Calendar service.
