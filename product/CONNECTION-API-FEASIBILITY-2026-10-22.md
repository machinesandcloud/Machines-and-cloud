# Connection API feasibility — October 22, 2026

**Decision:** automate the standard setup through provider APIs after the owner grants the necessary access. Offer optional specialist help for the remaining work, rather than making a specialist the normal onboarding path. API availability does not mean this repository already has a connector, that our app has vendor approval, or that a customer's plan permits it.

This is an architecture/research assessment of the local source and current official documentation. It performs no provider call, account connection, app registration, purchase, carrier submission or deployment. Current live readiness remains governed by [PRODUCT-STATUS](PRODUCT-STATUS.md); the unpublished combined phone/text coordinator is described in [the onboarding audit](ONBOARDING-AUTOMATION-AUDIT-2026-10-22.md). No automation percentage or immediate-activation promise is supported by this assessment.

## Platform-owned delivery

These are services M&C should configure for the customer. A shop should not need its own Twilio/Vapi developer account or copy provider API keys into ordinary onboarding.

| Service | What the official API can do | Owner action and external dependency | Current repository evidence |
|---|---|---|---|
| **Dedicated number: Twilio** | Search eligible inventory, acquire a number, set voice/SMS URLs, read configuration and release the resource. | Approve exact recurring/usage costs and authority. Available inventory, account funding and permitted execution remain prerequisites. | `lib/phone-twilio.mjs` already prices/searches/acquires, correlates uncertain outcomes and confirms release. `phone-activation.mjs` owns the durable request. API-supported and implemented behind gates; actual new-shop purchase/delivery is unaccepted. [IncomingPhoneNumber API](https://www.twilio.com/docs/phone-numbers/api/incomingphonenumber-resource). |
| **Phone receptionist: Vapi + Twilio** | Create/update an assistant and import a Twilio number with routing/server configuration. | Review business rules and a safe transfer destination, approve usage, and complete a real call test. Existing-line forwarding is a separate action. | `voice-provider.mjs` already creates/updates the assistant, imports the number, configures Twilio routing and reads it back. Existing workers recover saved work. This is not an automatic transfer of control over an arbitrary old phone line. [Vapi phone-number API](https://docs.vapi.ai/api-reference/phone-numbers/create). |
| **US business texting: Twilio** | Create customer secondary profiles, brands and campaigns; prepare dedicated messaging resources and inspect registration status. | Authorized representative confirms legal identity, EIN/address, consent program and costs. Carriers decide approval; corrections and setup-text reply can require the owner. | `messaging-provider.mjs` implements secondary profile/trust/brand/service/campaign/sender/webhook work. The supported validator is US EIN LLC/corporation/partnership, not every worldwide business. `service-onboarding.mjs` locally joins approved number → voice/SMS child requests. [ISV API guide](https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/onboarding-isv-api). |

Twilio recommends its customer-per-subaccount architecture for isolation, while also documenting shared-account/per-customer-service models. Our provider adapters currently use the configured account and per-shop resources; they do not create a subaccount per customer. Before scaling, decide and accept the account-isolation architecture rather than describing it as already implemented. The platform Primary Profile is a one-time console prerequisite; customers' secondary profiles can be automated. The M&C-only company campaign cannot register every shop. [Twilio ISV architecture overview](https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/onboarding-isv).

## Customer-owned calendars

| Connection | Feasible automation | Unavoidable permission / restriction | Current gap |
|---|---|---|---|
| **Google Calendar event sync** | Owner grants OAuth once; server exchanges the code, encrypts the refresh token, refreshes access and creates/changes/cancels supported saved visits in the background. | Owner chooses the Google identity and grants requested scopes. Revocation/expiry can require reauthorization. Publishing a consent screen to Production does not itself establish all required Google app verification. | Existing `calendar-connection.mjs` and `calendar-delivery.mjs` implement this for the primary calendar. The deployed UI requires a separate “Finish connecting” click. The new local `desk-connections.js` completes a matching fresh same-session return automatically after the authenticated workspace loads, using the existing owner action and unchanged server guards. Its actual-handler/browser fixture passes17/17; publication and real Google acceptance remain separate. [Local implementation and proof](CALENDAR-AUTO-CONNECT-2026-10-22.md), [Google server-side OAuth](https://developers.google.com/identity/protocols/oauth2/web-server). |
| **Avoid external calendar conflicts** | Google exposes `POST /calendar/v3/freeBusy`; use selected calendars, explicit time zone and bounded intervals to exclude busy periods. | Need a suitable additional permission: existing `calendar.events.owned` + `calendar.calendars.readonly` are not among the free/busy endpoint's documented accepted scopes. Owner may need a new consent grant. A calendar does not define technician skills, geographic routing, travel time or crew capacity. | Not implemented. Current sync writes M&C visits but does not read external busy time. Requires a separate scheduling design, race-safe final booking check, stale/error behavior and independent tests before making double-booking claims. [Free/busy API and scopes](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query). |

The immediate Google improvement is now implemented locally: completion of an **already granted** callback through the existing owner API. It preserves exact tenant/session/state/PKCE/lifecycle checks, denial handling, one-use behavior and session-expiry cleanup. An uncertain outcome clears the local callback and refreshes status; an absent connection can start fresh authorization. Legacy browser receipts retain the guarded explicit action. The unauthenticated callback still cannot exchange credentials, requested scopes are unchanged, and consumed authorization codes are not automatically replayed. The focused17/17, owner-API9/9, backend19/19 and existing Connections11/11 receipts use synthetic sign-ins, memory storage and intercepted provider responses, with no live action. This is narrower than adding free/busy or another calendar provider and is not yet deployed.

## Install website chat automatically where supported

No host-specific website installer exists in this repository. `embed.js` is a working widget/snippet surface, not a credentialed website connector. Detecting a platform from a URL can suggest the right route but cannot grant modification authority.

| Website platform | Supported installation route | Permission / plan / lifecycle limits | Proposed product treatment |
|---|---|---|---|
| **WordPress.org/self-hosted** | Publish a small M&C plugin that enqueues the tenant-bound widget. WordPress REST supports install/activate by WordPress.org plugin slug. Application passwords provide revocable API authentication. | Owner/admin must install/authorize with sufficient plugin capabilities; hosts can disable application passwords or plugin installation. The core install endpoint is not an arbitrary ZIP upload or general script-injection endpoint. Multisite and hosted WordPress restrictions need separate qualification. | Prefer an owner-installed plugin with a single-use workspace pairing flow; no main WordPress password. Later offer admin-authorized remote install where supported. We do not yet have a published plugin, pairing endpoint or verified installer. [Plugins REST API](https://developer.wordpress.org/rest-api/reference/plugins/), [application passwords](https://developer.wordpress.org/advanced-administration/security/application-passwords/). |
| **Wix** | Build/release an M&C app with an embedded-script extension. After owner installation, server calls Embed Script with the tenant parameter. | App access token/OAuth and Manage Embedded Scripts permission are needed. The extension must exist in a released app version; preview alone is insufficient. Updates/removal need lifecycle handling. | Good first website connector: “Connect Wix” → owner installs/authorizes → automatically embed → verify actual site. Direct install URL is documented; App Market publication is a separate distribution path. No current M&C app/connector is verified. [Embedded Script API](https://dev.wix.com/docs/api-reference/app-management/embedded-scripts/embed-script), [release/install requirements](https://dev.wix.com/docs/wix-cli/guides/extensions/site-extensions/embedded-scripts/about-embedded-scripts). |
| **Webflow** | OAuth app registers a versioned script, preserves existing scripts and applies it at site/page level. | Custom Code APIs require an OAuth Webflow App, not site/workspace tokens. Changes need publication, which releases **all staged site changes**. Official guidance says prompt the owner to publish; do not silently publish unrelated work. Marketplace code versions/review and uninstall scope retention also matter. | “Connect Webflow” → stage our versioned install → owner publishes → verify. This removes copying/pasting but does not justify hidden automatic publication. No connector exists here. [Custom Code guide](https://developers.webflow.com/data/docs/working-with-custom-code). |
| **Squarespace** | Supported code injection can place the widget on eligible sites. Current help lists Core, Plus, Advanced and some legacy plans. | Official developer entry lists Commerce APIs, Reseller APIs and a Custom Code specification. Reviewed public materials did **not establish a usable authenticated endpoint for editing an existing customer's code-injection settings**. The specification page exposed no endpoint contract in this review. Reseller account creation/linking does not establish script-install authority. | Guided copy/paste or an invited specialist while we obtain a documented supported automation route. Mark as assisted, not “API impossible” and not “Connect automatically.” Revisit new developer docs before implementation. [Code injection](https://support.squarespace.com/hc/en-us/articles/205815908-Customize-parts-of-your-site-with-code-injection), [developer platform](https://developers.squarespace.com/). |

Verify installations using the authorized public site and actual widget behavior. A stored script ID, successful API response, screenshot upload or customer checkbox alone is insufficient to label a channel ready. Preserve tenant/origin binding, avoid duplicate loaders, and remove only code created by our connector on disconnect.

## Home-service operating systems / CRM

These integrations should reuse the shop's existing customer/job workflow. They are not a shortcut for provisioning the shop's phone or giving us ownership of its business account.

| Platform | API and attainable automation | Access limits and owner action | Repository status / recommended first scope |
|---|---|---|---|
| **Jobber** | OAuth + versioned GraphQL support reading account data and scoped create/update mutations. Existing business/customer/job information can reduce repeated entry; supported lead/request writes can close the loop after specific schema validation. | A company admin grants OAuth. Draft apps connect to at most 5 paying accounts; review is needed for public distribution or lifting that cap. Refresh rotation/disconnect handling and end-to-end tests are review prerequisites. Do not mass-distribute an unreviewed connect URL. | No connector. Build a developer-test-account adapter first: import proposed business facts for review and create one deduplicated lead/request if supported by selected scopes; do not promise dispatch booking before validating the actual job/visit schema. [Getting started](https://developer.getjobber.com/docs/getting_started/), [GraphQL behavior](https://developer.getjobber.com/docs/using_jobbers_api/api_queries_and_mutations/), [review process](https://developer.getjobber.com/docs/publishing_your_app/app_review_process/). |
| **Housecall Pro** | Public API supports custom integrations; exact read/write objects must be qualified in its API reference. | Official self-managed path requires MAX plan and an Admin-generated key, with Read-only or Full access. Do not tell lower-plan owners the button will work. A general self-service OAuth entitlement/partner route was **not confirmed from official docs in this review**; contact HCP before promising one-click multi-customer OAuth. | No connector. Prefer vendor-approved partner connection if obtained; otherwise a secure, encrypted, revocable admin key handoff for eligible accounts. Never put the key in a draft, URL, analytics or chat. [Official API overview](https://help.housecallpro.com/en/articles/8505035-api-overview), [API reference](https://docs.housecallpro.com/). |
| **ServiceTitan** | APIs expose CRM, dispatch/capacity and other scoped operations using tenant-specific client credentials and the app key. | Third-party developers need ServiceTitan's assigned integration environment and reviewed public app. Customer enables the approved app; obtain tenant-specific credentials through the authorized workflow. Their FAQ expressly prohibits creating/registering our third-party app inside a customer's account to bypass that process. | No connector. Treat as partner/Enterprise rollout after integration access, schema tests and proper app approval; start with request capture before automatic technician booking. A specialist cannot remove vendor review or account permission requirements. [Developer access FAQ](https://developer.servicetitan.io/docs/faqs/developers), [first API call](https://developer.servicetitan.io/docs/getting-started/first-api-call). |

Do not claim every API exposes all receptionist settings or routing/dispatch decisions. A customer's scheduling system should remain the agreed source of truth. CRM writes need tenant-bound external IDs, deduplication, revision conflict handling, disconnect/revocation, recovery after unknown outcomes, and clear status distinguishing “saved here” from “confirmed in Jobber/HCP/ServiceTitan.”

## Delivery order and specialist boundary

1. **Complete the core API-managed service**, rather than making a new form: accept the approved isolated first-shop policy and demonstrate real number → phone → dedicated-shop texting plus recovery/cleanup. Keep gate decisions and spending authority explicit. This is closer to completion than any unbuilt website/FSM connector.
2. **Remove unnecessary connection steps:** automatically complete the granted same-session Google return; show denied/reconnect states; keep a clear current next action. Collect website platform and existing phone system once, reuse known business/contact facts, and show only capabilities we can actually deliver for that account.
3. **Build supported website installs**, starting with Wix and a WordPress plugin, then Webflow's staged-install/publish flow. Verify published-site function and uninstall. Use guided/assisted Squarespace and unsupported-host fallback while APIs are unqualified.
4. **Add Google busy-time protection as its own scheduling feature.** Define time zone, chosen calendars, refresh/revocation, stale availability and a race-safe final conflict check. Do not relabel the existing event writer “two-way sync.”
5. **Jobber first FSM connector**, subject to developer program rules and schema qualification; then eligible HCP and ServiceTitan partner paths. Validate import/lead capture before advanced dispatch automation. Prioritize real customer platform demand, not the longest integration-logo list.
6. **Use specialists for residual work:** unsupported site editors, legacy phone systems, number port/cutover planning, data cleanup and custom CRM mappings. They use scoped invitations or revocable access, record what changed and verify outcomes. They cannot impersonate a legal signature, Google consent or carrier decision. Technical work already supported by M&C's normal product should not become a surprise mandatory fee.

Pricing for that optional service needs a separately evidenced, clearly bounded package. Do not invent an “industry standard” amount from a platform API page. Capture a request/quote only until delivery scope, staffing, service terms and payment handling exist; no fake specialist booking or automatic charge should be shown.

Acceptance for each connector requires one newly authorized eligible tenant, a real read/write outcome in the intended external account, reconnect/disconnect/revocation, duplicate/unknown-result recovery and customer-visible progress. Until then label it as planned, locally tested or vendor approval pending, as appropriate. The customer should only answer business questions, grant access they control and complete genuine verification; routine vendor provisioning belongs to the platform.
