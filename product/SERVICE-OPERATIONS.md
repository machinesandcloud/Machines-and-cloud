Source inspection is local; it does not establish delivered messages, remote configuration, monitoring receipt or production readiness.

The operating goal is **a customer can enter, configure, test, activate an eligible service and recover from routine errors without Steve intervening**. The platform performs routine work. Customers supply business facts, authorize their own accounts, make service choices and complete provider-required declarations. Providers make their own approval decisions. OM owns platform exceptions and incidents, rather than asking the founder to shepherd every account.

Do not introduce asynchronous work merely to queue this deterministic path.

## Customer and operation states

One shop can have website chat active while SMS awaits carrier review. A single legacy `status` must not substitute for per-channel authority. Every setup operation stores its input revision, correlation ID, attempt count, next attempt, current claim and sanitized receipt. The owner sees the useful state and next action; secret/provider payloads remain private.

The following timings are **proposed acceptance policy, not an installed schedule**. Existing scheduler runs every ten minutes; current shop-wide scans are throttled to :00/:30. The new bounded setup recovery scan must be explicit and independent of that throttle.

| State | Customer action/view | Platform/provider action | Accountable owner / exit evidence |
|---|---|---|---|
| `waiting_customer` | A specific action: verify email, correct a field, review rules, grant OAuth or configure forwarding. Save/resume remains available. | Preserve prior valid work; no repeated paid steps. | Customer owns facts/consent. Platform owns a working action and return path; saved revision or verified event advances the state. |
| `queued` | “Your setup is queued”; no claim of service availability. | Persist work before dispatch. Trigger is a hint; recovery scan also finds it. Dispatch on the next scan, normally within ten minutes. | Engineer implements; OM monitors oldest eligible queued age. A durable claim, not an HTTP202, advances to running. |
| `running` | Show the current step and last update. | CAS claim/fencing; persist attempts before an external request. Respect configured deadlines and actual response. | Platform owns execution. A claim-matching receipt/result advances the operation. |
| `retry_due` | Explain a temporary issue and scheduled retry; allow leaving safely. | Only known-safe work retries. Proposed delays after attempt1/2 are one and five minutes; actual pickup occurs on the next ten-minute scan. Three attempts total per revision. | OM owns retry policy. No promise of an exact minute or repeated founder action. |
| `waiting_provider` | “Carrier review pending” or equivalent, plus when checked and any customer correction. Unrelated eligible services remain usable. | Poll an existing resource ID on an explicit schedule; do not create another one. | Provider owns approval; platform owns polling. Actual provider decision advances state. |
| `uncertain` | “We are checking the setup result”; unrelated channels stay available. No repeat purchase button. | Retain request/claim/receipt IDs; reconcile the original external effect. Never turn an expired timer into permission to purchase again. | OM owns the exception; architect defines reconciliation. Unknown is neither success nor safely retryable failure. |
| `failed` | A bounded reason, preserved inputs and useful correction/retry action. | Exhausted retry/rejected input remains durable and visible; alert the owned exception queue. | OM owns platform defects; customer owns only correctable business input. A new valid revision can create a new operation. |
| `succeeded` | Display only the capability actually proved. | Persist completion before dependent work and notification intent. | Receipt at current revision, then readiness derivation. A tutorial Next click is insufficient. |
| `cancelled` | Service stops as promised; resource cleanup remains separately visible. | Invalidate future claims, cancel pending work and reconcile remote resources. Late workers cannot reactivate anything. | Authenticated owner intent; cleanup receipts close the operation. Failed cleanup retains resource identifiers. |

No lease expiry allows an uncertain irreversible operation to run again. Read-only draft generation can use bounded, fenced retries only after the architect's claim/budget rules are implemented. SDK retries must count within the total attempt budget; do not hide multiple paid calls inside one recorded attempt.

## Duplicate, orphan and spend safeguards

1. One verified mailbox maps to one reserved tenant. Strict storage failure never means “new customer”; uncertain creation repairs the original reservation.
2. Every paid resource intent has current customer consent/cost selection and a product-wide enabled gate. A verified email, plan dropdown or onboarding completion is not cost consent. This gate is **off for new self-service provisioning now**.
3. Each provider creation gets its own durable claim and receipt. Messaging-service creation and number attachment are separate steps; A2P profile/product/brand/campaign are separate steps; assistant creation and number import are separate steps. Persisted IDs are reused on retries.
4. A lost provider response leads to reconciliation by supported idempotency/correlation, never blind recreation. A made-up idempotency header is not protection.
5. No stale worker can overwrite an owner edit, restore a paused/cancelled status or mark another revision tested. Completion is conditional on claim and configuration revision.
6. Cleanup keeps resources and indexes until remote outcomes are confirmed. A failed or skipped release is not `releasedAt`.
7. Spend counts are durable before requests and survive restart/retry. Per-shop and global limits, with explicit exhausted states, precede launch. No funds, recharge, purchase, filing or deploy is authorized here.
