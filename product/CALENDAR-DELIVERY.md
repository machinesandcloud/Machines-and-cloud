# Customer Calendar connection and delivery

The customer authorizes their own Google account from Connections. An operator does not copy tokens or configure an account for each shop. This implementation is locally exercised against intercepted Google HTTP responses; it has not connected a real customer account or changed a real calendar. Both execution gates remain off until provider acceptance is separately prepared and authorized.

## Customer and integration contract

`lib/calendar-connection.mjs` exposes `startCalendarConnection(c, session)`, `completeCalendarConnection(c, session, {state, code, error?})`, `disconnectCalendar(c, session)` and the safe asynchronous `calendarConnectionView(c)` (`calendarReadiness` alias). The root client handler must retain owner Bearer authentication, first-party Origin checks and strict request bodies for `start_calendar_connection`, `complete_calendar_connection` and `disconnect_calendar`. A permanent owner key and an operator session are not accepted.

Start returns a fixed Google authorization URL with a random opaque state, ten-minute lifetime, encrypted PKCE verifier and S256 challenge. The stored state binds the authenticated mailbox, exact owner session hash, tenant identity, latest calendar grant epoch and workspace lifecycle version. A newer connect attempt, disconnect, expiry, replay, changed tenant, changed lifecycle or wrong session prevents completion. State is atomically consumed once before token exchange. A denial is consumed without contacting Google and leaves any existing connection intact.

Google returns to `/api/google/callback`. This route sends a no-store/no-referrer 303 to the fixed `/desk?c=...` page with the returned code and opaque state in the fragment. It never exchanges tokens or accepts a tenant/key/redirect supplied by the callback. The signed-in portal strips the fragment and submits completion with the original owner Bearer session. The earlier permanent-key `/api/google/auth` entry is retired with 410. No owner key, session token or encoded business credential appears in OAuth state or URLs.

The supported target is the customer's owned primary Google calendar. Requested scopes are `calendar.events.owned` (event access on owned calendars) and `calendar.calendars.readonly` (calendar metadata). `GET /calendars/primary` obtains the concrete calendar ID so reconnecting a different Google account cannot silently send old records to another calendar. This does not request `calendar.readonly`, read external busy time, synchronize external appointments into availability or claim two-way synchronization. The Google project must approve and configure these exact scopes and the exact callback URI.

Refresh tokens are private in `calendar_connections`, sealed with AES-256-GCM, unique IV and authenticated connection binding. `CALENDAR_TOKEN_ENCRYPTION_KEY` must be a canonical base64 encoding of 32 random bytes supplied securely as environment configuration; it is never a public key or a checked-in value. Tokens, target IDs, tenant identities, claims and OAuth rows are excluded from client DTOs. `invalid_grant` clears the unusable credential and records `reconnect_required`. Disconnect stops local work immediately, invalidates pending grants and discards the local credential; it does not revoke the customer's whole Google grant, delete calendar events or erase delivery records.

Tenant identity is a SHA-256 hash of slug, the stored owner-key incarnation and normalized mailbox. Both credential/state and delivery paths re-read the authoritative client and verify that identity. A new customer reusing a slug and mailbox cannot reuse old Calendar credentials, OAuth grants or event references.

## Durable saved-visit delivery

`lib/calendar-delivery.mjs` exposes `queueCalendarBooking(c, booking)`, `calendarDeliveryView(c)`, `runCalendarDelivery({limit, discoveryLimit, budgetMs})`, `calendarDeliveryEnabled()`, `calendarEventId(c, bookingId)` and internal/test lookup `calendarDeliveryKey(c, bookingId)`. The caller supplies the full authoritative client object. Queueing is allowed only after the local booking commit; the helper re-reads the saved source inside every conditional-write attempt so a delayed enqueue cannot regress newer facts.

New self-service bookings must stamp `delivery.tenantIdentity = calendarTenantIdentity(c)`. Unstamped historical records do not silently backfill: they need a deliberate migration/ownership decision. This prevents retained bookings under a recreated slug from being copied into a new customer's calendar.

Each job is stored under `slug/tenantIdentity/bookingId` and owns one deterministic base32hex-compatible Google event ID. The desired source snapshot and monotonically increasing version survive failures. The event has private ownership, version and source-revision metadata. Timed windows preserve minute precision and use the explicit America/Chicago IANA zone in Google; invalid dates and untimed windows require attention rather than inferred times. Active visits create/update events; explicit cancellation removes the matching event; completed visits retain calendar history. Saved local bookings and capacity are authoritative and are never rolled back because Google is unavailable.

After a saved booking or completed OAuth connection, the root handler dispatches the fixed authenticated `/api/calendar-delivery-background` endpoint. `runCalendarDeliveryWave` holds a conditional shared lease, processes at most fifty eligible jobs and discovers at most two hundred source records within a shared two-minute budget; each provider job has at most twelve seconds. Concurrent triggers coalesce into the running wave. The dedicated scheduler dispatches the same worker every ten minutes to recover missed triggers. The background endpoint accepts only POST with an empty JSON object and the server-only `SERVICE_WORKER_KEY`; no caller selects a tenant, provider or work limit. Source discovery recovers a local commit whose immediate enqueue was lost. It considers future active visits for initial delivery and revisits retained job sources for changes/cancellation using fair cursors. No event is created merely by displaying a page. The main scheduler can read `health/calendarDelivery:lastRun`; dispatch status is recorded separately at `calendarDelivery:lastDispatch`.

A job claim is conditional and leased. Every mutation re-reads current source, claim, tenant, lifecycle and connection. Google GET observes the exact event ID and ETag. Writes use If-Match for update/delete; a conflicting version yields a retry. A stale worker cannot attach its receipt to a newer desired version. A provider request already accepted while a customer pauses or disconnects cannot be recalled; the next read reflects the retained event reference, and no subsequent write starts after the changed state is observed.

A durable `createAttempt` marker is saved before the initial insert and retained across every newer desired version. A 404 cancellation cannot be marked complete while an older creation is in flight or uncertain; a late successful insert records its observation into the newest job so cancellation can subsequently delete that exact event. An unknown create outcome never permits a second insert merely because GET is currently empty. A lost insert response is recovered by GET of the same deterministic ID. Insert 409 retrieves and verifies that event; it never mints a second ID. A foreign ownership marker, missing ETag, changed target or deleted-event tombstone requires attention rather than an overwrite or migration. A lost delete response is recovered with GET404/410 and confirmed without another deletion. Local results and receipts are conditionally saved only for the current job claim/version. Each desired version has at most five attempts with exponential backoff, after which it remains visible as `needs_attention`.

Paused, closed and unknown workspace states do not perform external writes. Only `testing` and `live` are accepted for delivery. Paused work and a locally disconnected calendar remain `waiting_connection` without consuming repeated provider attempts; a lifecycle change or a new same-target authorization creates a new desired version and can resume it. Reconnecting a different target never migrates existing jobs automatically. The portal receives counts and latest thirty safe job summaries; full retained counts are explicit. Expected waiting work is reported separately from failed retries and attention cases in worker health.

## Configuration and proof

- `CALENDAR_CONNECTION_ENABLED=true` is required for OAuth requests/token use; missing credentials or encryption key fails closed.
- `CALENDAR_DELIVERY_ENABLED=true` and a server-only `SERVICE_WORKER_KEY` of at least thirty-two characters are additionally required for worker execution. Both execution gates are off by default.
- `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` remain server-only environment settings.
- Customer consent, Google verification, the connection credential and calendar event delivery must be proven against a real authorized account before enabling service claims. Existing fake-model/local/publication permissions do not authorize that proof.

Engineering checks: `node scripts/calendar-connection-check.mjs` and `node scripts/calendar-delivery-check.mjs`. Each uses dummy credentials, memory conditional storage, intercepted production adapter requests and denied physical networking. Fresh `--output scratchpad/new-name.json` uses exclusive file creation and never overwrites prior evidence. `calendar-connection-engineering-final.json` retains 19 checks; `calendar-delivery-engineering-final.json` retains 23 checks before the expected-waiting health-count refinement. The current `calendar-connection-integrated-first.json` and `calendar-delivery-background-engineering-first.json` receipts cover 19 and 27 checks respectively. The independent `calendar-late-create-independent-wave.json` retains two checks for the delayed first-insert/cancellation race. The shared mailbox normalizer makes tenant hashes agree exactly across delivery engines. Rerun these checks against the integrated batch before release. Earlier engineering receipts used the fixture's controlled Date clock in their evidence timestamp; the final harness now records actual wall time separately from simulated retries.

The cases exercise actual OAuth endpoints and Calendar GET/POST/PATCH/DELETE adapter request contracts; state/session/tenant/lifecycle denial; encryption and minimal scope; lost response, duplicate insert, foreign event, latest reschedule, stale worker, concurrent worker, cancellation, failed provider, bounded attempts, safe DTO, fair discovery, same/different target reconnect, legacy/unknown records and scheduler gate-off. These checks do not establish actual Google acceptance, live Netlify storage concurrency or inbox/voice/text delivery. A wave is bounded by real elapsed provider time; the tested three-visit completion does not establish a production latency guarantee at fifty slow requests or unlimited tenant load. Retained-job reads and global failure census still need a pending-index/archive design and measured scale limits before broad rollout.
