# Operations: onboarding and delivery

How a shop goes from the pilot form to a live front desk, what runs where, and what Steve has to switch on once.

## Four-connection customer setup (local candidate)

The active connection-journey candidate reuses each shop's saved business answers. Selecting a connection records a preference; it does not authorize purchases, messaging or Google access. The customer stays in one workspace and is not asked to create Twilio, Vapi or Google Cloud developer accounts or supply API keys. Every chosen connection shows its current next step, the platform's work, the owner's one-time action and the evidence needed to call it ready.

| Connection | Customer supplies or authorizes | Background delivery | Ready evidence |
|---|---|---|---|
| Website chat | Website origin, reviewed answers, a private rehearsal, installation access or snippet installation | Prepare the saved front desk, serve the widget, retain the installation check and customer requests | Exact permitted website check, active chat and matching saved request; copying code is not installation |
| Phone answering | Existing business line/provider and routing choice or new-number choice; current usage/cost authority | Reserve one dedicated number, create/configure the assistant and webhooks, retain resource receipts and retry/reconcile safely | Current routing and a successful actual call; an existing-line owner/carrier must enable forwarding on that business line |
| Text messaging | Registered-business details and representative, customer consent process, current carrier/usage costs and setup-text agreement | Submit the shop's sender/brand/campaign, track review, configure inbound/status routes and delivery | Carrier approval and two-way setup verification; forwarding an existing voice line does not move its text messages |
| Google Calendar | Google OAuth permission for the intended account | Encrypt its refresh credential, discover saved visits, create/update/delete only the shop's deterministic owned event, reconcile retries | Owner grant and per-visit confirmed delivery; outside Google busy time does not yet alter offered availability |

Phone/text approvals name the exact available channel subset. A waiting SMS connection cannot block an already-authorized phone connection. Later availability alone cannot authorize a deferred service: its current costs and permissions require a separate explicit review. A later approval reuses the original shared number and retained setup receipts. Cancellation, changed owner identity, uncertain number acquisition and a changed common provider account still stop unsafe work. Worker progress survives browser closure; the visible page uses bounded refresh rather than an unlimited polling loop.

**Production Calendar policy is separate from the retained internal proof.** The new `CALENDAR_SELF_SERVICE_ENABLED=true` mode requires `CALENDAR_SELF_SERVICE_APPROVED_VERSION` and strict `CALENDAR_SELF_SERVICE_POLICY_JSON`: `mode: "self_service"`, `version`, future `expiresAt`, `googleClientIdHash`, `limits` and `tenantLimits`. Both limit objects contain exactly `oauthStart`, `tokenExchange`, `tokenRefresh`, `calendarRead`, `eventCreate`, `eventUpdate`, `eventDelete`, `workerDispatch`, and `totalRequests`; values are bounded nonnegative integers and each tenant ceiling is at most the global ceiling. Normal `CALENDAR_CONNECTION_ENABLED`, `CALENDAR_DELIVERY_ENABLED`, encryption/client credentials and the worker key remain required. These are platform deployment settings, never customer form fields.

This mode admits current opted-in workspace identities and their own owner-granted calendar and visits without hand-maintained slug/visit allowlists. Non-refundable per-tenant and global UTC-day CAS counters retain consumed capacity across policy version edits. Local desired work can remain queued during a pause or exhausted allowance, but local queue admission cannot authorize provider transport. OAuth state binds the original verified session, owner incarnation, grant epoch, Google client and policy; a changed client/policy cannot exchange an older code. Ordinary signout does not revoke the separately granted background connection. Disconnect, revoked Google permission, cancellation or ownership change prevents further delivery.

Website setup samples and simulated records are excluded from new delivery and checked again before a retained job can send email/SMS or touch Calendar. This candidate changes no production activation setting; the new self-service mode defaults off and the earlier named proof remains a separate closed phase. This candidate has local protocol-fixture evidence only; hosting restoration, Google branding/scope verification, current provider credentials and actual customer delivery are still launch gates. No environment or billing change is performed by these code changes.

## Managed owner-email admission

`MANAGED_EMAIL_BUDGET_POLICY_JSON` and its matching `MANAGED_EMAIL_BUDGET_APPROVED_VERSION` are server-only Functions settings for new self-service workspace `owner_booking` and `owner_lead` notifications. The ordinary automatic and scheduled managed outbox uses this same admission. Missing, invalid, expired or exhausted policy keeps the message saved in `waiting_platform` before a send attempt; it does not enable delivery. `SERVICE_DELIVERY_ENABLED=true`, the worker key, Resend configuration, current source ownership and ordinary workspace lifecycle still apply. Access/sign-in email and legacy `sendEmail` paths do not use this policy; their existing authorization and behavior remain separate.

The strict policy has exactly `version` (1–80 letters, digits, underscores or hyphens), `expiresAt` (future timestamp), `mode` (`cohort` or `self_service`), `providerCredentialHash` (SHA-256 of the exact configured `RESEND_API_KEY`), `senderHash` (SHA-256 of exact `FROM_EMAIL`), `accountLimit`, `tenantLimit` and `tenants`. Limits are safe integers from0 through1,000, with tenant at most account. Cohort mode requires1–25 distinct entries `{slug, identity, emailHash}`: the exact current workspace identity from `workspaceTenant(client)` and SHA-256 of the normalized verified owner email. The saved onboarding verification email must match the current owner. Never put plaintext keys, owner keys or bearer values in this policy or logs. `self_service` mode requires `tenants: []`; eligible verified owners then use the shared platform policy automatically without adding per-customer configuration. Choosing this broader mode remains a separate platform approval.

The one `managed_email_budgets` record at `resend:managed-owner:v1` holds cumulative non-refundable send reservations. It has no automatic day/month reset. Changing policy version, expiry, mode or cohort cannot replenish spent capacity. Exact immutable job replay reuses its reservation; changing recipient, purpose, body, source or tenant cannot reuse it. Reservation precedes the exclusive outbox claim and is rechecked before the actual provider POST. Unknown send results retain their debit and are never blindly resent. Known provider receipts can reconcile after the new-send policy expires or closes, while the ordinary global delivery gate still applies. Sender or credential changes fail closed against retained ledger custody; do not delete the ledger or rotate keys to reset it. Review an explicit custody/migration procedure before such a change.

This counts managed owner-email send attempts only. It does not cap all Resend requests, status inspections, sign-in/legacy mail, provider spend, API quotas or actual mailbox receipt. The1,000-reservation implementation bound is a pilot capacity, not demonstrated commercial throughput. A bounded production proof still requires exact recipients, retained-job census, a fresh effect scope and observed provider/mailbox receipts. Local synthetic delivery is not that proof, and these documentation/code changes configure no production policy.

## Managed REST SMS outbox and setup-text allowance

`MANAGED_SMS_BUDGET_POLICY_JSON` and matching `MANAGED_SMS_BUDGET_APPROVED_VERSION` are server-only Functions settings. Their absence, expiry, invalidity or a mismatched Twilio account blocks outbound managed REST SMS before its send-attempt marker. Setup texts use the same allowance as queued ordinary replies and visit messages. The outbox retains a waiting state, actionable reason and message; an approved policy can resume it. Existing delivery, sender, consent and lifecycle gates still apply. This is an exposure ceiling for the managed REST outbox and its setup texts, not the total Twilio-account bill. Synchronous TwiML keyword replies, carrier/provider-generated opt-out/help confirmations, inbound traffic, company/legacy SMS, registration fees, number rental and voice costs remain outside it. Required STOP behavior is preserved; activation cost review must account for these separate liabilities.

The strict policy object has exactly these fields: `version` (1–80 letters, digits, underscores or hyphens), `expiresAt` (future timestamp), `mode: "cohort"` or `"self_service"`, `providerAccountHash` (SHA-256 of the exact Twilio account SID), `currency: "USD"`, `rateBasis: "all_in_upper_bound"`, `rateSource` (HTTPS reference), `rates: {perMessageMicros, perSegmentMicros}`, `accountLimits: {messages, segments, costMicros}`, `tenantLimits` with the same three keys, and `tenants: [{slug, identity}]`. For a bounded proof, cohort mode lists at most25distinct current workspace SHA-256 identities, never slugs alone. For ordinary automated onboarding, self_service mode requires `tenants: []`: new eligible workspaces use the shared policy automatically, without per-shop configuration. Existing registered-sender, business approval, lifecycle and consent checks still authorize each send; the budget alone cannot register or activate a shop. Both modes share the same provider-account ledger and limits, so a mode change does not replenish capacity. All rates and limits are nonnegative safe integers; the segment rate is positive. Rates are at most100,000,000microdollars per message/segment. Limits are at most1,000messages,32,000segments and1,000,000,000,000microdollars; each tenant limit is at most its account limit. One microdollar is one millionth of a dollar. No account, tenant or rate is selected by a customer request.

Operations must supply a conservative upper bound covering the intended managed outbound destination and all applicable message/segment charges, including carrier surcharges on those sends. The code supplies no provider rate. It reserves `perMessageMicros + segments × perSegmentMicros` before transport. GSM-7 extension characters count twice; Unicode counts UTF-16 units. The conservative multipart packing uses152GSM-7 units or66Unicode units, also covering the smaller US/Canada toll-free allowance; it assumes no Smart Encoding substitutions. Payloads over1,600UTF-16units and non-`+1`numbers fail closed. [Twilio encoding and segment documentation](https://www.twilio.com/docs/glossary/what-sms-character-limit).

One conditional document per provider account atomically reserves the account and originating tenant's message, segment and cost totals. These are cumulative lifetime exposure limits for this bounded cohort, with no automatic day/month reset. Renewing a policy version or expiry retains spent capacity. Identical work reuses its reservation; changed content or sender cannot reuse it. Higher rate assumptions can only increase a prior reservation. Failures, ambiguous sends and unused reservations retain their debit. No send outcome refunds capacity or retries an unknown SMS. Raising limits requires an explicitly approved policy; these controls provide a bound under the supplied rate assumptions, separate from reconciliation against actual provider segment counts and invoices. Local synthetic-rate checks do not authorize activation or establish actual pricing.

## Managed number and initial carrier-registration admission

The server-only `MANAGED_RESOURCE_ADMISSION_POLICY_JSON` and matching `MANAGED_RESOURCE_ADMISSION_APPROVED_VERSION` control new managed number purchases and initial A2P brand/campaign filings. They add admission to the existing customer-approved offers, execution gates and worker authority. Missing, expired or insufficient admission waits before irreversible creation. It does not activate a service, approve a carrier filing, or replace the customer's legal and fee acknowledgments.

The exact policy keys are `version`, `expiresAt`, `mode`, `providerAccountHash`, `currency`, `rateBasis`, `rateSource`, `bounds`, `accountLimits`, `tenantLimits` and `tenants`. Use `currency: "USD"`, `rateBasis: "configured_upper_bound"` and an HTTPS `rateSource`. There are no default provider prices. `bounds` contains integer cents for `numberSetupCents`, `numberMonthlyCents`, `brandSetupCents`, `campaignSetupCents` and `campaignMonthlyCents`. Both limit objects contain `numbers`, `brands`, `campaigns`, `setupCents` and `monthlyCents`; tenant limits cannot exceed account limits. Disabled resource kinds with account count0 may use zero cost bounds; admitted kinds require positive rental/registration bounds. Number setup can explicitly be zero. This permits a number-only proof without inventing unused registration rates. `providerAccountHash` binds the configured Twilio account. An exact proof uses `mode: "cohort"` and up to25 `{slug, identity}` entries, where identity is the workspace-incarnation identity. `mode: "self_service"` requires `tenants: []` and admits eligible new shops under the shared account and per-shop ceilings without adding a founder-maintained entry for each signup.

One durable CAS ledger jointly reserves resource counts, non-refundable setup-fee assumptions and monthly recurring commitments for the tenant and account. One operation/kind retains one financial reservation; policy versions, mode changes, a new day, errors and unknown provider results do not reset it. Reservations are conservative lifetime debits, including unused holds and confirmed cleanup. `monthlyCents` limits the sum of configured monthly commitments; it does not limit total money charged across future months. The ledger has a bounded500-reservation capacity. Changing the provider account does not migrate or reset that ledger or any bound operation; migration requires an explicit recovery plan.

Reservations bind the provider account, workspace incarnation, stable operation, accepted financial offer and actual creation payload. Registration also binds its input and submission revision. An untouched number intent can retain its financial hold through a fresh review of changed business answers; changing the selected inventory number cannot silently reuse a different reserved payload. An observed account-specific number rental quote above the configured rental bound is denied before purchase, even if the customer offer permits more. Configured registration costs remain operator-supplied upper assumptions and require current provider pricing review before activation; they are not invoice measurements. Bounds above the customer's accepted fees or recurring price are denied.

Policy and current operation authority are checked again at the actual POST boundary. Capacity rejection clears only the invocation's definitive unsent dispatch marker; a dispatched or unknown attempt keeps its existing reconciliation path and reservation. Paid brand/campaign corrections are outside this first creation policy and cannot send an unbudgeted correction POST. They wait for separate correction admission. Existing recorded-resource lookup and cleanup do not consume another creation reservation and remain account-bound; the original global gates and brake still apply. A retained operation that lacks an established provider-account binding requires platform review; a404 from the currently configured account is not proof that its old resource was released. An expired phone offer blocks fresh acceptance and acquisition, while the same approved version, account, credentials, global execution gate and brake still govern recorded-resource maintenance. Missing or malformed offers keep maintenance closed.

This policy covers managed first-number acquisition and initial A2P brand/campaign creation only. It excludes call usage, texts and carrier segments, inbound traffic, provider add-ons, taxes, company/legacy paths and the complete provider bill. The separate managed REST SMS allowance still applies to setup texts and customer replies. Neither local synthetic prices nor a published code change authorizes production policy values, purchases, registration fees or activation.

## Recovering accepted customer setup

If business answers change after the number request is queued, the number worker first records a confirmed stop before purchase. A fresh shared owner review can then resume the same stable number request, including several corrections made before the next worker turn. A purchase attempt, unknown result, retained resource, cancellation or secondary-service handoff keeps its reconciliation path. Parent approval and cancellation are checked again before a number purchase; adding another channel does not invalidate an already accepted number.

Self-service Calendar jobs that reach a daily action allowance wait until the next UTC reset without consuming a failed-operation retry. Previous provider failures and unknown event creations retain their evidence. Scheduled recovery reconciles the same event; this does not replenish an old named proof allowance.

An expired texting verification, changed owner mobile, or invalidated renewed review offers **Request a new setup text** in Connections. The owner explicitly requests one fresh text to the current saved mobile. `renew_messaging_probe` accepts only `expectedRevision`, `operationId`, `expectedProbeNonce` and `testPhoneConsent: true` through the verified owner endpoint. It retains registration, sender, number and old-probe history; it does not refile a brand or campaign. Current reviewed facts and carrier/sender verification are required. A live or malformed worker lease cannot be overwritten. Changed or current nonces cannot be reused, and history is retained for up to20 renewals before support review.

Queued old checks cannot send after replacement. An unknown earlier send keeps its debit and is never retried. Both fresh transport and final delivery proof recheck the current mobile and reviewed revision. A later owner correction requires a new explicit verification request, with no seven-day wait. Recent delivery status displays retained explanations and Calendar's next eligible retry time; platform capacity approval remains an operator responsibility.

## The flow

1. **Pilot form** on the homepage posts to Netlify Forms (Steve gets the email) and sends the owner to `/onboard` with name, email, website, and phone prefilled. The plan buttons go straight to `/onboard?plan=...`.
2. **Onboarding** (`onboard.html` -> `POST /api/onboard`): five short steps (you, shop, prices and windows, rules, phone and leads). Creates the client record in Netlify Blobs with a private owner key, emails the owner their portal link, notifies Steve, and starts the build.

## Storage (Netlify Blobs, site-wide)

Stores: `clients` (slug -> record), `index` (`email:`, `number:` -> slug), `conversations` (`slug/channel/contact`), `bookings`, `leads`, `events` (`slug/id`), `tasks` (`dueISO_id`). Everything is JSON. There is no dashboard; use `/api/admin` or the Netlify Blobs UI.

### Booking capacity and interrupted writes

`index/capacity:<slug>` holds active booking reservations. Strong reads and conditional writes (`onlyIfNew`, then `onlyIfMatch` with the current ETag) arbitrate across function instances. Initial migration reads every booking, without a history limit. Equivalent ranges such as `8 to12`, `8-12`, and `8 AM to 12 PM` share capacity; `booked`, `confirmed`, and `on_the_way` occupy it.

Each booking mutation owns a token in that document. A reschedule holds both source and target until its booking writes finish. Competing updates reject with a retry message. Ordinary active updates also require the booking's reservation to exist, so a delayed confirmation cannot revive a completed cancellation. Tokens never expire. **Every booking-write exception retains the token and held capacity**, including a final 4xx: an earlier SDK retry may already have committed. This can block an unused slot until reconciliation. A full reschedule changes no booking, reminder, Calendar event, or notification.

Recovery is an engineer operation; there is no recovery endpoint:

1. Stop all booking writers for the affected shop, including chat, SMS, voice, owner/admin commands, and scheduler work. Confirm every old invocation has ended and cannot resume; elapsed token age is not proof.
2. Archive the capacity document and affected booking. Strong-read the persisted booking and current capacity ETag. If storage cannot be read, leave the reservation held.
3. With a conditional ETag write, reconcile only that booking ID: retain its canonical persisted date/window if its status is active above, otherwise remove its reservation. Remove its mutation token in the same write, preserving other bookings. If the ETag changed, reread and reassess before retrying.
4. Review partial reminders, Calendar changes, and notifications before resuming writers. A recovered reservation does not prove these effects completed; do not resend them blindly.

### Owner availability

The owner portal's **Availability** tab blocks a whole Houston date or one listed arrival window. Use it for work booked elsewhere, time off or a closure; maintain those blocks manually. This is not Google, Jobber or Housecall Pro busy-time synchronization. Existing visits remain booked, and their reserved count is shown beside each block. Emergency safety and human handoff still apply on a blocked date. Remove a block to reopen only the space left after other blocks and reservations.

Owner GET includes `availabilityBlocks`; owner POST accepts `{action:"availability_block"|"availability_unblock", date:"YYYY-MM-DD", window:""|listedLabel}`. An empty window means the whole date. Invalid input returns 400; an unavailable read or uncertain save returns 503 `availability_unavailable`. Reload before retrying an uncertain save. Repeating an add/remove is idempotent. At most 100 blocks are retained, including past blocks, which the owner can remove.

Blocks share `index/capacity:<slug>` with reservations and mutation tokens. Recovery above must preserve the entire `blocks` array. A reservation claimed before a block may finish; the block prevents subsequent new claims without moving or canceling prior visits. Chat, SMS and Vapi use `get_availability` to read listed openings for 1–14 dates; commit-time booking and reschedule also enforce the stored limits. Known numeric windows whose end has passed in Houston are unavailable for new claims that day. Office hours, named-window times and overnight scheduling are not inferred. Lookup failure is an error, not an empty or open calendar.

## Provisioning (automatic, after the build)

`provision-background.mjs` runs as soon as the build finishes and again whenever the owner saves registration details (portal action `provision`):

1. **Number.** Buys a local Twilio number in the shop's area code (falls back to 713/281/832/346), points voice to `/api/voice` and messaging to `/api/sms`, indexes it to the client.
2. **Messaging Service** with the number attached (needed for 10DLC).
3. **10DLC registration** through Twilio's API: Secondary Customer Profile (legal name, EIN, address, owner as authorized representative) -> A2P Trust Product -> Brand. The scheduler polls the brand every 10 minutes; when approved it files the campaign (MIXED use case: customer care, reminders, follow-ups) and polls again; when verified it marks `phone.tenDlc = approved` and tells the owner texting is live. Needs the owner's legal name, EIN, and address (asked in onboarding step 5 and on the portal) and `TWILIO_PRIMARY_PROFILE_SID` (Machines & Cloud's own approved Primary Customer Profile, a one-time console setup under Trust Hub with business type "ISV Reseller or Partner").
4. **Phone answering** through Vapi: three function tools (`get_availability`, `book_visit`, `notify_owner`) pointing at `/api/vapi`, an assistant with the client's prompt (voice variant) and `claude-sonnet-5` (override with `VAPI_MODEL`), the Twilio number imported into Vapi with `smsEnabled: false` so our SMS webhook stays. Vapi then answers forwarded calls; `/api/vapi` runs the shared availability, booking and owner-handoff tools during the call and files the transcript on `end-of-call-report`. Without `VAPI_API_KEY`, forwarded calls get the missed-call text-back instead.
5. **Owner instructions.** Text and email with the number and the exact forwarding code for their carrier (AT&T, Verizon, T-Mobile, VoIP, other), also shown as tap-to-dial buttons on the portal. The first forwarded call that reaches `/api/voice` marks forwarding verified. (Vapi-answered calls do not pass through `/api/voice`; the owner can press "I did this".)

Every step that lacks a key records `waiting: ...` in `provision.steps` and Steve gets one email listing what is missing. Nothing blocks the website chat or the portal.

Fallbacks and alerts: every number bought gets `VoiceFallbackUrl` and `SmsFallbackUrl` from `VOICE_FALLBACK_TWIML_URL` and `SMS_FALLBACK_TWIML_URL` (two TwiML Bins Steve creates once in the Twilio console). The voice bin is a Mustache template, exactly:
`<Response>{{#cell}}<Dial timeout="25">{{cell}}</Dial>{{/cell}}<Say voice="Polly.Joanna">We are having trouble connecting right now. Please call back in a few minutes.</Say></Response>`
Provisioning appends `?cell=%2B1...` for a shop whose owner cell is not the forwarded line and leaves the bare URL for a one-phone shop; the URL is re-set when the owner changes the cell, business number, or forwarding mode on the portal (`syncVoiceFallback`), on pause (the bin with the cell) and resume (`/api/voice` on a Vapi line). The SMS bin is `<Response><Message>We got your text and will reply shortly.</Message></Response>`. Twilio Debugger webhook: in the console under Monitor, Alerts, set the webhook to `https://machinesandcloud.com/api/twilio-alert` and turn on email alerts; each failure Twilio sees (11200 could not reach the webhook, 11205 timeout, 30034 unregistered sender) is logged as `twilio_error` on the shop whose number appears in the request and counts toward the alerts below. Vapi calls that end with a platform error (`assistant-request-returned-error`, `pipeline-error-*`, `*-llm-failed`, and the other failure families) log `voice_failed` from the end-of-call report. A Vapi-answered number gets `VoiceFallbackUrl` set to our `/api/voice` after the import, so a Vapi outage degrades to the missed-call text-back. The scheduler texts and emails Steve, once per hour per shop, when three or more texts failed in an hour or any voice failure was logged in the last 15 minutes, and once per five days when a live shop with verified forwarding has had no inbound call or text for five business days (`health_alert` event with `reason`).

## Serving the pages from another host (groundwork for a pause-proof site)

Every page carries `<meta name="mc-api-base" content="">` and the widget, portal, onboarding, and admin scripts read it: empty means same origin (today), a value such as `https://api.machinesandcloud.com` points every API call at Netlify while the HTML, CSS, and scripts live on a static host a Netlify pause cannot reach. `embed.js` on a customer's site takes `data-api` for the same purpose. On the Netlify side, `SITE_ORIGINS` (comma-separated) adds the static host's origin to the chat and onboarding allow-lists, and the client and onboarding functions answer with CORS headers. ## Testing without spending Netlify credits

Hosted test traffic uses Netlify request, compute and deployment credits, and a day of test loops exhausted the plan on 2026-10-20. The rule since then: verification runs locally and nothing goes to Netlify except one authorized git push per verified batch.

- `MC_LOCAL_NO_KEYS=1 MC_FAKE_MODEL=1 node scripts/local-server.mjs` serves the site and every function at `http://127.0.0.1:8888` from the production modules, without model spending. It forces memory storage and local background URLs, listens only on loopback, and refuses dotfiles such as `.env` and `.git/config`. The admin key is `local-admin`; `MC_MEMORY_FILE=.local-store.json` saves the listed synthetic business stores across restarts, not the voice/rate budget stores. The server loads `.env`; without explicit fake mode an available Anthropic key can make real model calls. Never treat a fresh memory process as a fresh external test allowance.
- Twilio, Vapi, Resend, Google, and Stripe API credentials are removed by default, including when `.env` contains live credentials. For real-model rehearsals use `MC_LOCAL_NO_KEYS=1 MC_FAKE_MODEL=0 node scripts/local-server.mjs`; this retains Anthropic access while messages and provider provisioning remain disabled. Local Vapi requests use `x-vapi-secret: local-vapi-secret` (override with `LOCAL_VAPI_WEBHOOK_SECRET`). Only an explicitly authorized real-provider pass uses `MC_LOCAL_NO_KEYS=0`. Use a fresh synthetic snapshot for rehearsals, rather than restoring production customer records.
- A separately authorized browser-voice rehearsal uses `MC_LOCAL_NO_KEYS=1 MC_LOCAL_VOICE=1` to retain server-side `VAPI_API_KEY` and `VAPI_PUBLIC_KEY` while removing every other provider credential. Keep fake versus real Anthropic mode explicit. The flag is not a network guard or a spending authorization: allow only the approved loopback/API destinations and exact provider operations, cap actual HTTP requests including retries, and preserve the cumulative ledger across process restarts. This scope creates browser practice calls only; it does not authorize phone dialing, provisioning, inbox messages or production writes.

## Testing without real accounts

- Start the local server above with a fresh synthetic memory snapshot. Draft deploys use the site's environment variables and shared Blobs store; they are not an isolated substitute for this local pass.
